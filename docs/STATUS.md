- **Parser Step 5**: full expression precedence chain (`logic_or` down to `unary`), the non-associative comparison/equality chain detection (E0101 fires for real now, including cross-level cases like `a == b == c`), bitwise-binds-tighter-than-comparison verified explicitly. Along the way, found and fixed a real miscalibration in the depth bound (redundant Step 4 hooks made paren/call/index nesting cost 3x what unary nesting did - see the separate "Remove redundant depth hooks" commit) and then empirically proved the fix: 255 levels of nested parens/unary/index/calls parse successfully, 256 and 300 all cleanly give E0103, uniformly across all four constructs, under both plain and ASan, zero crashes (`tests/parser/depth_*`). Mixed nesting (`!(!(!(...)))`) costs 2 depth units per level as expected, capping at 127/128. 75 golden tests total, 100% line coverage on `parser.c`.
- **Parser Step 6**: `let`/`return`/`break`/`continue` statements and the `block` wrapper, plus `type` (including nested array types `[1][1]...T`, self-recursive with its own depth hook - the same reasoning as `unary`'s). `parser_parse_block` is the new public entry point; `parse_block` carries a depth hook proactively (no cycle closes through it yet - Step 7's `if`/`while`/`for` will close one). Empirically proved nested array types the same way Step 5 proved expression nesting: 254 levels parses, 255 and 300 both cleanly give E0103 (one less than the standalone-expression 255, because `block`'s own hook already costs 1 of the 256 units) - `tests/parser/depth_type_*`, plain + ASan. 102 golden tests total, 99.02% line coverage on `parser.c` (the one gap - `parse_block`'s own `'{'` check - is justified, not fixed: unreachable through the current harness, which only calls it after peeking `'{'`; becomes reachable and will get real coverage once Step 7's `if`/`while`/`for` call it after a condition).
- **Parser Step 7**: `postfix_stmt`/`expr_tail` left-factored dispatch (assignment vs. plain expression statement, decided by one token of lookahead right after `postfix` - `parse_expr_tail` resumes the precedence chain at `multiplicative` and above with the already-parsed `postfix` as the initial operand, reusing all 10 precedence functions via a `given_lhs` parameter rather than duplicating them), plus `if`/`while`/`for`. The assignment-as-condition diagnostic (E0102) fires for real now (`if x = 5 {` / `while x = 5 {`). `a = b = c;` and `1 + 2 = x;` both fail exactly where M2_PLAN.md's grammar comment says they must, with no bespoke handling needed. `parse_block`'s `'{'` check (justified-uncovered since Step 6) is now reachable and tested (`if x return;` etc.). `parse_if_stmt` carries its own depth hook for the else-if self-recursion (`if -> else -> if`, a cycle that doesn't pass through `parse_block` at all - unlike real if/while/for nesting, which does). Empirically proved both: true nesting (`if a { if a { ... } }`) caps at 127/128; else-if chains cap at 254/255 - different numbers because different sets of counted functions are open simultaneously at each level, not a single "nested block" constant (`tests/parser/depth_nested_if_*`, `depth_elseif_*`, plain + ASan, zero crashes). 135 golden tests total, 100% line coverage on `parser.c`.
- **Parser Step 8**: top-level items - `translation_unit`/`version_decl`/`struct_decl`/`function_decl`, `parser_parse_file` the new public entry point. `manna v0;` required as the first line, with three distinct dedicated-vs-generic treatments: `manna` altogether absent is the new E0107 (with a fix-it inserting `manna v0;` at 1:1); `manna` present but malformed after that is generic E0105; `manna` present and well-formed but the wrong version (e.g. `manna v1;`) is the new E0106. Struct fields require a trailing comma on every field, including the last (part of `field_decl`'s own grammar, not a separator). Functions parse `{ attribute }` lists, params, and an optional `-> type` (absent = unit, stated explicitly, never inferred). Naming-convention enforcement and unknown-attribute/duplicate-name checks are explicitly deferred to the IR stage, not implemented here (recorded as locked decisions in `docs/M2_PLAN.md` §7 items 7-8). Depth invariant: Step 8 introduces no new cycle (confirmed by call-graph inspection, then empirically re-confirmed - nested-if inside a real function body still caps at exactly 127/128, identical to Step 7's standalone-block figure, proving `function_decl`/`top_level_item`/`translation_unit` add zero extra depth cost). 160 golden tests total, 100% line coverage on `parser.c`. The parser now reads whole `.mn` files end to end, matching M2_PLAN.md's own documented canonical dump example byte-for-byte.

- **Parser Step 9**: consolidated every depth-bound proof from Steps 5-8 into one table (`docs/M2_PLAN.md`'s "Depth-bound proof summary") - all 8 cycles (7 real + the confirmed-absent 8th), each mapped to its counted function, a construct example, and its proven succeed/fail boundary. Added the one gap found while consolidating: Step 8's "nested-if inside a real function body still caps at 127/128" claim had been verified ad hoc but never persisted as a golden test - now is (`depth_nested_if_in_function_127_ok`/`128_fail`). 162 golden tests total, no new code (this step touched docs and tests only, not `parser.c`'s logic).
- **Parser Step 10**: panic-mode error recovery (`docs/M2_PLAN.md`'s new "Error recovery (Step 10, implemented)" subsection has the full design) at two granularities - statement-level and top-level-item-level. A malformed statement/item is dropped (no placeholder node) and parsing resumes at the next sync point, instead of aborting the whole enclosing block/file. Two real bugs found and fixed by writing and reading golden tests carefully: (1) a brace-nesting-unaware skip could stop at an inner `;`/`}` belonging to the declaration being recovered from, orphaning its real closing `}` and causing a spurious second error - fixed by tracking brace depth while skipping; (2) the sync set was missing statement-start keywords (`let`/`if`/`while`/`for`/`return`/`break`/`continue`), so a skip in progress could silently swallow an entire subsequent valid statement - fixed since it's always safe (every one of those seven keywords is unconditionally consumed by its own parse function before it can fail, so landing on one mid-recovery can never be a zero-progress situation). One known, documented limitation left as-is: a malformed `for`-loop init can still produce two diagnostics from one root cause, since the remaining `cond`/`step` clauses happen to be independently-valid statement shapes once reinterpreted fresh - fixing this needs a third (for-loop-clause-level) recovery granularity, deliberately not added. All required properties tested directly: no infinite loop (a statement illegally starting with `fn` inside a block terminates cleanly), no cascade (one mistake -> one error, both at statement- and top-level-item granularity), the depth counter is provably uncorrupted after a recovered error (255/256 nested parens immediately after one), and the existing 20-error fatal cap still aborts everything exactly as before once actually reached. 169 golden tests total, 100% line coverage on `parser.c`.

- **Parser Step 11**: determinism (`make test-determinism`, `tools/run_determinism_test.sh`) - every existing lexer and parser golden-test input (182 total) run through the plain binary twice and byte-compared, then the ASan binary once more and byte-compared against the plain run too. Zero drift found either way. Deliberately separate from the golden-file tests themselves, which only check output against a fixed expected text, not run-to-run/build-to-build stability directly.

- **Parser Step 10b**: replaced Step 10's ad-hoc per-level recovery functions with one systematic mechanism - Wirth-style follow-set recovery (`docs/M2_PLAN.md`'s new "Error recovery (Step 10b, implemented)" subsection has the full design, including the level -> resume-tokens -> masks table). Each syntactic level (top level, block, statement, header) declares its own resume-token set and is tracked as currently active or not via one counter per level in `ParserState`; one shared skip finds the first depth-0 token matching any active set, and ownership (does the level that just failed recognize this token as its own?) decides whether to resume locally or propagate, trusting whichever level truly owns the token to recognize it once control unwinds there. Found and fixed one real design gap the literal mechanism didn't resolve on its own, by testing rather than assuming: the uniform "stop at first match of any active set" rule, as first implemented, did NOT actually fix the for-init double-diagnostic cascade (verified - it reproduced the exact old two-error output byte-for-byte), because a `for`-header's own internal `';'` separator is indistinguishable by token kind from the enclosing statement's own resume point, so recovery stopped there instead of searching on for the header's `'{'`. Fixed with one declared mask (`sync_for_header`, documented in `parser_state.h`): while a `for`-header is unresolved, it masks statement's `';'` specifically; `if`/`while`'s headers declare no such mask, since their condition is a bare `expression` that can never contain a `';'` (proved with a contrasting pair of tests - `{ if ; y; }`/`{ while ; y; }` both still recover cleanly at the `';'`). This also fixes the original motivating bug in passing (confirmed, not just claimed): a header failure with no body ever found before the next real `fn` no longer swallows that function (`err_recovery_header_no_body_before_fn`). One accepted trade-off, deliberately not fixed: the mask is coarse, not clause-aware, so content between a `for`-header failure and the next unmasked stop is silently discarded rather than preserved or re-reported (`err_recovery_for_header_mask_swallows_filler`) - strictly better than Step 10's cascade, but still loss; documented, not solved. All 169 pre-existing goldens re-verified (only the one for-init golden's output actually changed, confirmed by diffing every other one, byte-for-byte unchanged); 11 new goldens added covering the required cases plus the masking contrast pair and two coverage gaps (a `for`-header's cond/step clauses failing, not just its init). 180 golden tests total, 99.80% line coverage on `parser.c` (the one gap - the top-level loop's last-resort single-token-skip backstop - is justified, not fixed: unreachable under the current grammar, since every top-level dispatch path already guarantees progress some other way before that backstop would ever be needed; kept anyway as a real enforced guarantee rather than relying on that chain of reasoning staying true forever, same precedent as `parse_block`'s own proactively-added `'{'` check back in Step 6).

- **Parser Step 12**: libFuzzer harnesses for the lexer and parser (`make fuzz`/`fuzz-lexer`/`fuzz-parser`, `tools/fuzz/run_fuzzers.sh`, `tools/mannac/fuzz_lexer.c`/`fuzz_parser.c`) - libFuzzer + ASan + UBSan, seeded directly from the existing golden-test inputs. Apple's Xcode clang ships no libFuzzer runtime at all (confirmed: `-fsanitize=fuzzer` fails to link); uses brew's keg-only llvm instead. Deliberately not in CI - run locally for a fixed wall-clock budget. Aimed specifically at error recovery per request: the parser corpus is seeded with every `err_recovery_*.mn` golden, and the parser binary is built with `MANNA_FUZZ_TRACE_LAST_RESORT` (compiled out of every other build), which turns `parser_parse_file`'s last-resort single-token-skip backstop into an immediate, saved crash if ever actually reached - empirical proof one way or the other, not just the reasoning in Step 10b's commit message. First run: lexer 2,328,111 execs in 181s, parser 480,689 execs in 601s - zero crashes, zero timeouts, zero sanitizer reports on either target, and the last-resort backstop was never hit. No golden tests added this run (the instruction is "every crash becomes a golden test" - none occurred).
