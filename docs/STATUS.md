## Known issues in `m2-parser-v0`

- **FIXED in typed-IR step 2b (E0111, limit 512; see Done) - kept here as the record for the `m2-parser-v0` tag.** **Tree height is not bounded by the nesting-depth bound, and `expr_print` (the AST dump) overflows the host stack on a tall tree.** The depth bound counts recursion *cycles*; left-associative binary chains (`1+1+1+...`) and postfix chains (`a.f.f.f...`, `a[0][0]...`) are built by loops, so a flat input makes a tree as tall as it is long, at no depth cost. Measured on `c6a4cf0` with `parser_dump` built from the Makefile's sources, one `let x = <chain>;` in a function, default 8 MB stack: 20,000 terms (all three shapes) overflows the stack in `expr_print` under ASan+UBSan; the plain `-O2` build survived 100,000 terms; the same ASan binary passes with a 64 MB stack; 200,000 terms gives E0110 (arena cap), no tree. The parser itself is unaffected (it builds these trees iteratively); the only bound on height is the 16 MiB arena. So `docs/M2_PLAN.md` §4's "never a host-stack overflow" holds for the parser and not for anything that walks its output. Separately, the dump's output grows quadratically with chain length (indentation per level; ~20 GB at 100,000 terms). No golden or fuzz run has hit this. **Fix:** a tree-height bound in the parser, E0111, limit 512 (step 2b of `docs/TYPED_IR.md`).

- **Parser Step 10**: panic-mode error recovery (`docs/M2_PLAN.md`'s new "Error recovery (Step 10, implemented)" subsection has the full design) at two granularities - statement-level and top-level-item-level. A malformed statement/item is dropped (no placeholder node) and parsing resumes at the next sync point, instead of aborting the whole enclosing block/file. Two real bugs found and fixed by writing and reading golden tests carefully: (1) a brace-nesting-unaware skip could stop at an inner `;`/`}` belonging to the declaration being recovered from, orphaning its real closing `}` and causing a spurious second error - fixed by tracking brace depth while skipping; (2) the sync set was missing statement-start keywords (`let`/`if`/`while`/`for`/`return`/`break`/`continue`), so a skip in progress could silently swallow an entire subsequent valid statement - fixed since it's always safe (every one of those seven keywords is unconditionally consumed by its own parse function before it can fail, so landing on one mid-recovery can never be a zero-progress situation). - **Parser Step 10b**: replaced Step 10's ad-hoc per-level recovery functions with one systematic mechanism - Wirth-style follow-set recovery (`docs/M2_PLAN.md`'s new "Error recovery (Step 10b, implemented)" subsection has the full design, including the level -> resume-tokens -> masks table). Each syntactic level (top level, block, statement, header) declares its own resume-token set and is tracked as currently active or not via one counter per level in `ParserState`; one shared skip finds the first depth-0 token matching any active set, and ownership (does the level that just failed recognize this token as its own?) decides whether to resume locally or propagate, trusting whichever level truly owns the token to recognize it once control unwinds there. Found and fixed one real design gap the literal mechanism didn't resolve on its own, by testing rather than assuming: the uniform "stop at first match of any active set" rule, as first implemented, did NOT actually fix the for-init double-diagnostic cascade (verified - it reproduced the exact old two-error output byte-for-byte), because a `for`-header's own internal `';'` separator is indistinguishable by token kind from the enclosing statement's own resume point, so recovery stopped there instead of searching on for the header's `'{'`. Fixed with one declared mask (`sync_for_header`, documented in `parser_state.h`): while a `for`-header is unresolved, it masks statement's `';'` specifically; `if`/`while`'s headers declare no such mask, since their condition is a bare `expression` that can never contain a `';'` (proved with a contrasting pair of tests - `{ if ; y; }`/`{ while ; y; }` both still recover cleanly at the `';'`). This also fixes the original motivating bug in passing (confirmed, not just claimed): a header failure with no body ever found before the next real `fn` no longer swallows that function (`err_recovery_header_no_body_before_fn`). One accepted trade-off, deliberately not fixed: the mask is coarse, not clause-aware, so content between a `for`-header failure and the next unmasked stop is silently discarded rather than preserved or re-reported (`err_recovery_for_header_mask_swallows_filler`) - strictly better than Step 10's cascade, but still loss; documented, not solved. All 169 pre-existing goldens re-verified (only the one for-init golden's output actually changed, confirmed by diffing every other one, byte-for-byte unchanged); 11 new goldens added covering the required cases plus the masking contrast pair and two coverage gaps (a `for`-header's cond/step clauses failing, not just its init). 180 golden tests total, 99.80% line coverage on `parser.c` (the one gap - the top-level loop's last-resort single-token-skip backstop - is justified, not fixed: unreachable under the current grammar, since every top-level dispatch path already guarantees progress some other way before that backstop would ever be needed; kept anyway as a real enforced guarantee rather than relying on that chain of reasoning staying true forever, same precedent as `parse_block`'s own proactively-added `'{'` check back in Step 6).
