# Manna compiler error code registry

Stable codes for `manna check --json` (docs/M2_PLAN.md §7 item 4). A code, once assigned, is **never reused or renumbered** — if a diagnostic is retired, its code retires with it rather than being recycled for something unrelated.

Ranges, reserved by pipeline stage (docs/M2_PLAN.md §3):

| Range | Stage |
|---|---|
| `E00xx` | Lexer (assigned retroactively at JSON-schema implementation time — the lexer's existing error kinds in `tools/mannac/lexer.h` predate this registry) |
| `E01xx` | Parser |
| `E02xx` | Typed IR / type checking |
| `E03xx` | Static pointer verifier |
| `E04xx` | Codegen (loop-counter injection, Wasm backend, native backend) |

## E01xx — Parser

| Code | Message | Meaning | Fix hint |
|---|---|---|---|
| `E0101` | `comparisons can't be chained; use a < b && b < c` | Two comparison/equality operators in one expression (`a < b < c`) — non-associative by design (docs/M2_PLAN.md, comparison/equality grammar). | None - documented exception. The natural rewrite, `a < b && b < c`, evaluates `b` twice and isn't a single-span edit, and only the author knows whether double evaluation is acceptable; the message itself carries the suggestion. |
| `E0102` | `assignment is a statement; did you mean '=='?` | A condition is followed by `=`: `if`/`while` found it where the condition-terminating `{` was expected, and a `for` header's condition clause found it where the clause-terminating `;` was expected (`for ...; i = 5; ...`). Three call sites in `tools/mannac/parser.c`, all the identical call `parser_error(p->ps, diag_assignment_as_condition(p->ps->arena, token_span(p->cur)))` guarded by `if (p->cur.kind == TOK_ASSIGN)`: in `parse_if_stmt` (after the condition), in `parse_while_stmt` (same), and in `parse_for_stmt` (after the condition clause, before the `';'` check). The JSON `expected` field is `'{'` at the `if`/`while` sites and `';'` at the `for` site (`diag_assignment_as_condition` takes it as a parameter; it was hardcoded to `'{'` through `m2-parser-r1`, wrong at the `for` site, fixed in #4 step 0 and pinned in `parser_fixes_test.c`). | Replace the single `=` with `==`. |
| `E0103` | `maximum nesting depth (256 units) exceeded` | The parser's one shared nesting counter went past its cap of 256 **depth units**, so the file is abandoned (a safety bound against host-stack overflow, not a style rule). Units are not levels: each recursive construct costs 1 unit per level, so 255 nested parens parse and 256 is the first to fail, but combined constructs cost more per level (`!(...)` is 2) and the budget is shared with every enclosing counted construct (a nested array type caps at 254 inside a block, not 255). The full rules, the per-construct proof table and the golden tests live in `docs/M2_PLAN.md` "Universal nesting-depth bound" and "Depth-bound proof summary" - the owner of this topic; this row deliberately does not restate them. | None - documented exception: the input has to be restructured, there is no mechanical edit. |
| `E0104` | `too many errors, stopping` | Error count reached `MAX_ERRORS` (20) in one file; parsing stopped early as a safety valve against cascading noise. | None - documented exception: fix the earlier errors first; the cap is a cascade guard, so there is nothing to apply. |
| `E0105` | `expected X, found Y` (template) | Generic syntax error — every parse failure that isn't one of E0101/E0102 above goes through this one constructor (`diag_expected`, `tools/mannac/diag.c`), so the message format lives in one place. `X`/`Y` vary per call site (e.g. `expected ')' after expression, found '}'`). | None by default - documented exception: a generic expected/found has no single canonical repair (the right fix depends on author intent). A site gets its own code and fix-it only when a mechanical repair exists (E0102, E0107, E0108, E0109). Candidate sites for a real fix-it (e.g. a missing `;`) and their cost are tracked in `docs/history/R1_TRIAGE.md`, not implemented. |
| `E0106` | `unsupported manna version 'vN' (expected 'v0')` | The file's `version_decl` (`manna IDENT;`, required as the first non-comment line - MANNA_PRINCIPLES.md Part 4 item 1) has `manna` present and a well-formed identifier that isn't `v0`. A `manna` keyword present but malformed after that (no identifier, no `;`) is E0105 instead; `manna` altogether absent is E0107 instead. | None - documented exception: rewriting the version to `v0` would assert the file is v0-compatible, which only its author can know (and there is no v1 to migrate to yet). |
| `E0107` | `missing version header; add 'manna v0;' as the first line` | The file's first token isn't `manna` at all (as opposed to `manna` being present but malformed or the wrong version - E0105/E0106). | Insert `manna v0;` as the file's first line (fix-it provided, inserting at 1:1). |
| `E0108` | `comparison and equality can't be mixed without parentheses; use (a < b) == c` | **Emitted since #4 step 5.** An operand of `&&`/`\|\|` (or a lone expression) contains two comparison/equality operators of *different* class, e.g. `a < b == c` or `a == b < c`; both are accepted today and become errors. Same-class repeats (`a < b < c`, `a == b == c`, `a == b != c`) stay `E0101`, with no fix-it. docs/M2_PLAN.md §4 `relational` + "Reserved words, constructors, and conversions". | Two zero-width inserts (two edits in the fix): exactly one `(` and one `)` inserted around the comparison-class pair (`<,>,<=,>=`, from its left operand's first character to its right operand's last), nothing else changed: `a < b == c` -> `(a < b) == c`; `a == b < c` -> `a == (b < c)`. |
| `E0109` | `'-> unit' is not written; omit the return type` | **Emitted since #4 step 6.** An explicit `-> unit` followed by the body's `{`. `unit` is a reserved word but not a writable type; "returns nothing" is spelled by omitting the annotation. The function stays in the tree (no return type) and its body is parsed. `-> [3]unit` and `-> unit[3]` are not this error: they stay the generic E0105. | Deletions only: one edit removing exactly `-> unit` when `->` and `unit` share a line with only blanks between; otherwise two edits removing the `->` token and the `unit` token separately, keeping any comment or line break between them. |
| `E0110` | `input too large: the compiler's memory limit was exceeded` | **Emitted since the v0 audit fix (F2).** The compiler's working-memory cap (the arena, 16 MiB for the parser harness) was exhausted; parsing stops there and no tree is produced. Recorded once, at the last token read. Before this, the same exhaustion unwound silently: an empty error list and no tree. Cheap to hit with a generated input (a ~900 KB array literal or call argument list), never with hand-written code. Registered in the parser range because the arena belongs to the parser state; any later stage that adds its own cap gets its own code. | None - documented exception: the only remedy is a smaller input (split the file or the literal), which is not an edit at a place. |

**Documented exceptions (r1 Phase B) - generic `E0105`, no dedicated code and no fix hint, by design:** a reserved word (`u8`..`i64`, `bool`, `unit`) where an identifier is required; `unit` in any type position other than after `->` (that one site gets `E0109`); an empty array literal `[]`; a repeat count that isn't an integer literal (`[v; X]`); conversion arity/shape (`u8()`, `u8(a, b)`, a bare `u8` in expression position). Each is a plain expected/found mismatch already fully described by `diag_expected`'s template; a rename or a different construct isn't a single-span mechanical edit. Rationale and exact wordings: docs/M2_PLAN.md "Diagnostics added by r1 Phase B".

IR-stage diagnostics implied by the same spec (struct-construction field checks, array-literal element types, conversion operand/target types, lvalue validity, ...) are listed in that section without codes; the `E02xx` range is assigned when the IR stage starts.
