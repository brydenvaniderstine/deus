# Manna compiler error code registry

Stable codes for `manna check --json` (docs/M2_PLAN.md §7 item 4). A code, once assigned, is **never reused or renumbered** — if a diagnostic is retired, its code retires with it rather than being recycled for something unrelated.

Ranges, reserved by pipeline stage (docs/M2_PLAN.md §3):

| Range | Stage |
|---|---|
| `E00xx` | Lexer (assigned retroactively at JSON-schema implementation time — the lexer's existing error kinds in `tools/mannac/lexer.h` predate this registry) |
| `E01xx` | Parser |
| `E02xx` | Typed IR / type checking |
| `E03xx` | Static pointer verifier |
| `E04xx` | Codegen (loop-counter injection, Wasm backend, native backend) |

## E01xx — Parser

| Code | Message | Meaning | Fix hint |
|---|---|---|---|
| `E0101` | `comparisons can't be chained; use a < b && b < c` | Two comparison/equality operators in one expression (`a < b < c`) — non-associative by design (docs/M2_PLAN.md, comparison/equality grammar). | None - documented exception. The natural rewrite, `a < b && b < c`, evaluates `b` twice and isn't a single-span edit, and only the author knows whether double evaluation is acceptable; the message itself carries the suggestion. |
| `E0102` | `assignment is a statement; did you mean '=='?` | A condition is followed by `=`: `if`/`while` found it where the condition-terminating `{` was expected, and a `for` header's condition clause found it where the clause-terminating `;` was expected (`for ...; i = 5; ...`). Three call sites in `tools/mannac/parser.c`, all the identical call `parser_error(p->ps, diag_assignment_as_condition(p->ps->arena, token_span(p->cur)))` guarded by `if (p->cur.kind == TOK_ASSIGN)`: in `parse_if_stmt` (after the condition), in `parse_while_stmt` (same), and in `parse_for_stmt` (after the condition clause, before the `';'` check). The JSON `expected` field is `'{'` at the `if`/`while` sites and `';'` at the `for` site (`diag_assignment_as_condition` takes it as a parameter; it was hardcoded to `'{'` through `m2-parser-r1`, wrong at the `for` site, fixed in #4 step 0 and pinned in `parser_fixes_test.c`). | Replace the single `=` with `==`. |
| `E0103` | `maximum nesting depth (256 units) exceeded` | The parser's one shared nesting counter went past its cap of 256 **depth units**, so the file is abandoned (a safety bound against host-stack overflow, not a style rule). Units are not levels: each recursive construct costs 1 unit per level, so 255 nested parens parse and 256 is the first to fail, but combined constructs cost more per level (`!(...)` is 2) and the budget is shared with every enclosing counted construct (a nested array type caps at 254 inside a block, not 255). The full rules, the per-construct proof table and the golden tests live in `docs/M2_PLAN.md` "Universal nesting-depth bound" and "Depth-bound proof summary" - the owner of this topic; this row deliberately does not restate them. | None - documented exception: the input has to be restructured, there is no mechanical edit. |
| `E0104` | `too many errors, stopping` | Error count reached `MAX_ERRORS` (20) in one file; parsing stopped early as a safety valve against cascading noise. | None - documented exception: fix the earlier errors first; the cap is a cascade guard, so there is nothing to apply. |
| `E0105` | `expected X, found Y` (template) | Generic syntax error — every parse failure that isn't one of E0101/E0102 above goes through this one constructor (`diag_expected`, `tools/mannac/diag.c`), so the message format lives in one place. `X`/`Y` vary per call site (e.g. `expected ')' after expression, found '}'`). | None by default - documented exception: a generic expected/found has no single canonical repair (the right fix depends on author intent). A site gets its own code and fix-it only when a mechanical repair exists (E0102, E0107, E0108, E0109). Candidate sites for a real fix-it (e.g. a missing `;`) and their cost are tracked in `docs/history/R1_TRIAGE.md`, not implemented. |
| `E0106` | `unsupported manna version 'vN' (expected 'v0')` | The file's `version_decl` (`manna IDENT;`, required as the first non-comment line - MANNA_PRINCIPLES.md Part 4 item 1) has `manna` present and a well-formed identifier that isn't `v0`. A `manna` keyword present but malformed after that (no identifier, no `;`) is E0105 instead; `manna` altogether absent is E0107 instead. | None - documented exception: rewriting the version to `v0` would assert the file is v0-compatible, which only its author can know (and there is no v1 to migrate to yet). |
| `E0107` | `missing version header; add 'manna v0;' as the first line` | The file's first token isn't `manna` at all (as opposed to `manna` being present but malformed or the wrong version - E0105/E0106). | Insert `manna v0;` as the file's first line (fix-it provided, inserting at 1:1). |
| `E0108` | `comparison and equality can't be mixed without parentheses; use (a < b) == c` | **Emitted since #4 step 5.** An operand of `&&`/`\|\|` (or a lone expression) contains two comparison/equality operators of *different* class, e.g. `a < b == c` or `a == b < c`; both parsed before #4 step 5 and are errors now. Same-class repeats (`a < b < c`, `a == b == c`, `a == b != c`) stay `E0101`, with no fix-it. docs/M2_PLAN.md §4 `relational` + "Reserved words, constructors, and conversions". | Two zero-width inserts (two edits in the fix): exactly one `(` and one `)` inserted around the comparison-class pair (`<,>,<=,>=`, from its left operand's first character to its right operand's last), nothing else changed: `a < b == c` -> `(a < b) == c`; `a == b < c` -> `a == (b < c)`. |
| `E0109` | `'-> unit' is not written; omit the return type` | **Emitted since #4 step 6.** An explicit `-> unit` followed by the body's `{`. `unit` is a reserved word but not a writable type; "returns nothing" is spelled by omitting the annotation. The function stays in the tree (no return type) and its body is parsed. `-> [3]unit` and `-> unit[3]` are not this error: they stay the generic E0105. | Deletions only: one edit removing exactly `-> unit` when `->` and `unit` share a line with only blanks between; otherwise two edits removing the `->` token and the `unit` token separately, keeping any comment or line break between them. |
| `E0110` | `input too large: the compiler's memory limit was exceeded` | **Emitted since the v0 audit fix (F2).** The compiler's working-memory cap (the arena, 16 MiB for the parser harness) was exhausted; parsing stops there and no tree is produced. Recorded once, at the last token read. Before this, the same exhaustion unwound silently: an empty error list and no tree. Cheap to hit with a generated input (a ~900 KB array literal or call argument list), never with hand-written code. Registered in the parser range because the arena belongs to the parser state; any later stage that adds its own cap gets its own code. | None - documented exception: the only remedy is a smaller input (split the file or the literal), which is not an edit at a place. |
| `E0111` | `expression too long: more than 512 chained operations in one expression; split it into several statements` | **Emitted since typed-IR step 2b.** An expression tree grew taller than `MAX_EXPR_HEIGHT` (512, `ast.h`). Height counts nodes on the longest root-to-leaf path; parentheses add nothing. The nesting-depth bound (E0103) counts recursion cycles, but left-associative binary chains and postfix chains (`a.f.f...`, `a[0][0]...`) are built by loops, so without this a flat input makes a tree as tall as it is long and overflows any recursive walker's stack (measured, with the choice of 512: `docs/M2_PLAN.md` "Typed IR (stage 3)", Input contract). Fatal, like E0103: the file is abandoned and there is no tree. Located at the token that follows the node whose construction crossed the limit. The limit is on total height, so deep nesting combined with long chains can reach it too. | None - documented exception: the input has to be split into several statements (e.g. `let` bindings); there is no mechanical edit. |

**Documented exceptions (r1 Phase B) - generic `E0105`, no dedicated code and no fix hint, by design:** a reserved word (`u8`..`i64`, `bool`, `unit`) where an identifier is required; `unit` in any type position other than after `->` (that one site gets `E0109`); an empty array literal `[]`; a repeat count that isn't an integer literal (`[v; X]`); conversion arity/shape (`u8()`, `u8(a, b)`, a bare `u8` in expression position). Each is a plain expected/found mismatch already fully described by `diag_expected`'s template; a rename or a different construct isn't a single-span mechanical edit. Rationale and exact wordings: docs/M2_PLAN.md "Diagnostics added by r1 Phase B".

## E02xx — Typed IR

`E0202` is deliberately unassigned (it was a dropped proposal, an IR-side tree-height bound; the bound lives in the parser as `E0111`). The number is not reused.

|---|---|---|---|

| `E0213` | `'x' is already declared in this function` | **Emitted since typed-IR step 7.** A `let` whose name is already visible: a parameter, or a local of the same or an enclosing block (no shadowing at all, `docs/M2_PLAN.md` "Names, scopes, items"). | `E0220` | `unknown type 'X'` | **Emitted since typed-IR step 4a.** An identifier in type position names no struct; a function's name used as a type is the same error. Reported at the identifier. Inside `[N]T` the one error is reported at the identifier and the enclosing array is silently ERROR (no second diagnostic). | None - documented exception: the intended type is unknowable from the text. |
| `E0221` | `struct 'S' contains itself` | **Emitted since typed-IR step 4b.** A struct holds itself *by value*: directly (`struct Node { next: Node, }`), through other structs, or through arrays (`[3]A`), since an array holds its element. One error per cycle (per strongly connected component of the "holds" relation, so overlapping cycles are one), reported at the name of the cycle's **lowest-declaration-index** member. No struct in the cycle gets a layout, and structs that merely hold a cyclic struct stay silent (the mistake is already reported). Slices cannot close a cycle (a slice is not allowed in a field, E0227). | None - documented exception: breaking a cycle means choosing which field to remove or redesign. |
| `E0222` | `type is too large (size exceeds the limit)` | **Emitted since typed-IR step 4b.** A type whose size would exceed `2^31 - 1` bytes (`docs/M2_PLAN.md` "Layout and limits"), including by arithmetic overflow while computing it: an array `[N]T` whose `N * size(T)` exceeds it, reported at that array type (the innermost one that overflows); a struct whose fields, alignment padding, or trailing padding take it over, reported at the struct's name. An array of a zero-size element is zero-size whatever `N` is, so `[18446744073709551615]Empty` is legal. At most one E0222 per struct (the first failing field); structs that hold a too-large struct stay silent. **Since typed-IR step 12 also an array literal or `[v; N]` whose type `[len]T` exceeds the limit** (`[n; 2147483648]` with `n: u8`, `[big, big]` with `big` of `2^30` bytes), reported at the whole literal. | None - documented exception: the type has to be smaller, which is not an edit at a place. |
| `E0223` | `type mismatch: expected T, found U` | **Emitted since typed-IR step 6b (the workhorse code for the later steps' mismatches).** An expression's type is not the one expected of it. `U` is a type name, or `integer literal` for an untyped integer literal expression, which has no type until one is expected of it (`expected bool, found integer literal`); a bool literal is `bool`. Reported once for the whole offending expression (`1 + 2 * 3` where `bool` is expected is one error at the start of the group, never one per literal, and no range errors are reported underneath it), and the expression is then ERROR-typed, so enclosing checks are silent. | None - documented exception: which side to change is the author's call. |
| `E0224` | `integer literal N does not fit in T` | **Emitted since typed-IR step 6a.** An integer literal outside its type's range. `N` is the literal in decimal as written; a literal *directly* under unary minus is reported with its sign and located over the whole `-N` (`integer literal -129 does not fit in i8`), while a parenthesized one, `-(129)`, is reported as plain `129` at `(129)`. The magnitude `2^(N-1)` directly negated is the signed minimum and fits (`-128` in `i8`); `-(128)` does not. An out-of-range literal does **not** poison: its type stays the expected type, so every bad literal in an expression reports on its own. A literal of 2^64 or more is a lexer error and never reaches this stage. | None - documented exception: which value was meant is the author's call. |
| `E0225` | `cannot infer the type of this integer literal; annotate it` | **Emitted since typed-IR step 7.** An integer literal expression (`0`, `-1`, `1 + 2`) with no expected type: `let i = 0;` or `5;` as a statement. Reported at the whole literal expression; the binding it initializes is still declared, typed ERROR, so `let j: u8 = i;` afterwards is silent. | None - documented exception: the intended type is the author's call (the message says to annotate). |

| `E0280` | `'x' is not snake_case` | **Emitted since typed-IR step 14.** A function, struct field, parameter, `let` local or `for` loop variable whose name is not `snake_case` (`[a-z][a-z0-9]*('_'[a-z0-9]+)*`: no leading, trailing or doubled `_`, no capital: `fooBar`, `_x`, `x_`, `a__b`, `X`). | `E0252` | `can't index/slice type T` | **Emitted since typed-IR step 12.** `a[i]` or `a[lo..hi]` whose base is not an array or a slice (an integer, `bool`, a struct, a call result). Reported at the base expression; the index or bounds are then checked for their own mistakes only; the expression is ERROR-typed. An integer literal as a base has no type to name (`E0225`); a unit call is `E0226`. Messages are in source order: the base is validated before the index. | None - documented exception: the author's call. |
| `E0253` | `index/bound must be an integer, found T` | **Emitted since typed-IR step 12.** An index or slice bound of a type other than an integer (`bool`, a struct, an array). Any integer type is fine (Q7: no conversion to a "usize"). Reported at the index or bound; the indexing keeps the element type, so the mistake does not spread. An integer *literal* index or bound takes `u64` (so `a[9]` on a `[4]u8` is accepted: out-of-range literals are the verifier's, not an error here, while `a[-1]` is `E0260`, unary `-` on an unsigned type). | None - documented exception: the author's call. |
| `E0254` | `len takes exactly one argument, found N` | **Emitted since typed-IR step 12 (specified 2026-10-18, Admission #15, `docs/M2_PLAN.md` "Arrays, slices, storage").** A call `len(...)` with zero or two or more arguments, or a named argument (`len(x: a)`). Reported at the call; the arguments are still checked for their own mistakes only, and the call still has type `u64`. A named argument is worded `found a named argument` (`len(v: a)`), the count otherwise. (Registered ahead of its first emission at the author's instruction on 2026-10-18; the "register when first emitted" rule of `docs/history/TYPED_IR.md` section 5 was waived for E0254-E0257.) | None - documented exception: which argument was meant is the author's call. |
| `E0255` | `len needs an array or a slice, found T` | **Emitted since typed-IR step 12.** The argument of `len(x)` has a type other than `[N]T` or `[]T` (an integer, `bool`, a struct). Reported at the argument. An integer literal argument has no type to name (`E0225`). An argument that is already ERROR-typed gives no `E0255`, and the result is still `u64`. | None - documented exception: the author's call. |
| `E0256` | `len is a builtin function; call it as len(x)` | **Emitted since typed-IR step 12.** `len` used other than as a direct call: `let f = len;`, `len + 1`. Reported at the name, and **only when no VISIBLE declaration named `len` exists**: a bare `len` that resolves to a declaration made despite `E0257` is quiet, one that appears after the scope of such a declaration closed (`if c { let len: u8 = 1; } let n = len;`) resolves to nothing and is `E0256` as well (a second mistake: the declaration is `E0257`), and `len(...)` always means the builtin. In practice that is a local or loop variable: a struct, function or parameter named `len` is an `E0257` in the declaration pass, which stops the build before any body is read. | None - documented exception: the call to write needs its argument. |
| `E0257` | `'len' is a builtin and can't be declared` | **Emitted since typed-IR step 12.** A function, struct, local or parameter named `len` (Q3: a name means one thing; a struct field named `len` is legal). Reported at the declaration's name; the declaration still binds, so a later bare `len` that resolves to it is quiet (no `E0256`), and `len(...)` always means the builtin. | None - documented exception: the new name is the author's call (a rename fix-it would need every use). |
| `E0260` | `operator 'op' is not defined for T` | **Emitted since typed-IR step 6a (unary `-` on an unsigned type); step 8 completes the operator/type table.** The operator has no meaning for an operand's type: arithmetic (`+ - * / %`), bitwise (`& \| ^`), shift and ordering (`< > <= >=`) take integers only, so bool, a struct or an array is this error (`bool & bool` included: `&&` is the boolean operator, one way to write it); `==` `!=` also take bool but not structs or arrays; `&&` `\|\|` `!` need bool (`!x` with an integer `x` is this error); unary `-` needs a signed integer (`-x` with `x: u32`, and `-1` where an unsigned type is expected), unary `~` any integer. Reported once per operator expression at the whole expression, naming the left operand's type if it is the offender, else the right's; the expression is then ERROR-typed. A literal operand has no type to name: under `!`, `&&` and `\|\|` it is `E0223` (`expected bool, found integer literal`). | None - documented exception: which operator or type was meant is the author's call. |
| `E0261` | `operands have different types: T and U; convert one explicitly` | **Emitted since typed-IR step 8.** The two operands of a binary operator are both allowed for it but have different types: no implicit conversion exists (a shift's count must also be the left operand's type). Reported once at the whole expression. A literal operand never causes it (it takes its sibling's type); `u8 == bool` does (an integer and a bool). Poisons the expression, so nothing built on it reports again. | **Two integer types: wrap exactly ONE operand in a LOSSLESS widening to the other's type**, as two zero-width inserts (`T(` before the operand, `)` after it - no source text needed, the E0108 mechanism; the operand's span includes its parentheses): the operand that converts without loss (`u8 + u32` -> `u32(a) + b`; an unsigned type converts to a wider signed one). If neither direction is lossless (`u8` and `i8`) there is **no fix**; a fix never narrows. A shift wraps only its count, into the left operand's type, and only if that widens the count. The fix is offered only where the binary's resulting type is known to be accepted: **(a)** a comparison (the result is `bool` whichever operand is wrapped), anywhere; **(b)** a place that expects exactly the new result type - a `return`, an annotated `let`, an argument, a construction field, an array element, an assignment - and from there the same place for the operand of unary `-` (which must then be signed) and `~`, for **both** operands of an arithmetic or bitwise parent and for a shift's left operand; **(c)** an unconstrained value (an un-annotated `let`, an expression statement), and through unary `-` or `~`, but not through a parent operator. Anywhere else (a condition, an index, a conversion operand, an operand of a comparison or `&&`) there is no fix. A fix inside an arithmetic, bitwise or shift parent is also withdrawn when the parent's other operand is a typed expression of another type (it would make the parent fail): `a + b + c` with `a: u8`, `b: u16`, `c: u8` returning `u16` has no fix. `return u32(a) + b;` in a `-> u8` function, a count that would be narrowed and `u8 + i8` have none either: a fix that leaves the program rejected is worse than none. Pinned by `tools/mannac/ir_e0261_exhaustive.c` (`make test-e0261-exhaustive`: every offered fix is one lossless wrap and re-checks clean), `ir_test.c` and `tests/ir_fix/fix_e0261_*` (audit findings 4 and F1/F4, steps 17-18). With a bool or a struct no integer conversion exists: no fix. |
| `E0265` | `can't convert T to U; conversions are between integer types only` | **Emitted since typed-IR step 13.** A conversion `U(x)` where `U` or the operand's type `T` is not an integer type: `bool` on either side (`bool(x)`, `u8(b)`, `bool(b)`), or a struct, array or slice operand. Reported at the whole conversion; the result keeps the target type `U`, so the mistake does not spread. An integer converted to `bool` appends `(write 'x != 0')`; there is deliberately no spelling for `bool` to integer (principle 1). The operand is typed on its own, never from the target: a bare literal operand (`u8(255)`, `u8(300)`, `u32(-1)`, `u8(1 + 2)`) has no type and is `E0225` at the operand, and a unit call is `E0226`. A same-type conversion (`u8(x)` with `x: u8`) is legal, a no-op, and kept in the IR. An ERROR operand is silent. | None - documented exception: `x != 0` needs source text the fix mechanism does not carry. |
| `E0270` | `can't assign to this expression` | **Emitted since typed-IR step 7.** The target of `=` is not an lvalue. An lvalue is a plain name, or a field or element of an lvalue (`x`, `p.f`, `a[i]`, `p.f[i].g`); everything else is this error: a literal, a call, a conversion, an array literal or an element of one (`[1, 2][0]`), a binary expression, a slice expression (`a[0..2]`), a field of a non-lvalue (`g(x).y`), and any **parenthesized** target (`(a) = 1`, `(p).x = 1`: the productions have no parentheses). Decided on the target's shape alone, before anything is typed, so a bad target is one error and none of its parts is blamed for anything else (a muted walk records its call edges, so recursion through it is still E0235, and its name uses, so renames reach them); the value is still checked for its own mistakes, against no type. Reported at the whole target. | None - documented exception: what to assign to is the author's call. |
| `E0275` | `'break' outside a loop` / `'continue' outside a loop` | **Emitted since typed-IR step 8.** `break` or `continue` that is not lexically inside the body of a `while` or `for` (an `if` inside a loop body is still inside it; an `if` outside any loop is not; the `for` header's init and step are not part of the body). Reported at the statement; the statement is still built, so nothing cascades. The parser accepts them anywhere. | None - documented exception: the loop (or a different statement) is the author's call. |
| `E0276` | `missing return value: function 'f' returns T` / `unexpected return value: function 'f' returns nothing` | **Emitted since typed-IR step 9.** A `return` whose shape does not match its function: `return;` in a function that returns a type (reported at the statement), or `return v;` in a function that returns nothing (reported at the VALUE; `v` is still checked for its own mistakes, against no type, so `return nope;` is also E0230). | `E0277` | `function 'f' may end without returning a value` | **Emitted since typed-IR step 9.** A function that returns a type can reach the end of its body without a `return` (docs/M2_PLAN.md "missing return", decision Q5). **Structural**, no constant folding: a block returns if ANY of its statements does (statements after a `return` are unreachable, which is allowed); a `return` does; an `if` does only with an `else` and when the then-block and the else both do (an else-if chain is an else that is itself an `if`). **Loops never count** (`while true { return 1; }` and a `for` whose body returns still need a `return` after them), and `break`/`continue` return nothing; `if true { return 1; }` without an `else` does not return.
